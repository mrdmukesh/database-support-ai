## Relationship and booking diagnostics

The failing run planned primary and related queries, but correlation expansion used only the ranked metadata
subset. Related active-schema tables could therefore be described in discovery/report metadata without being
queried. Expansion also labelled every multi-row ID correlation as “duplicate correlated rows.” Three rows that
share `BookingsId` are not proof of duplication; a dedicated duplicate count or repeated business/correlation key
is required.

The fix expands safe correlation queries to ID-bearing tables from active normalized metadata and labels them
“correlated rows.” SQL validation, query limits, and read-only execution remain unchanged.

## Policy and after-state

The implemented policy is constrained policy B:

- Broad exploratory request + verified business key/rows: provider may produce an evidence-only timeline and
  must state that no defect was reproduced. Status: `AI_SUMMARIZED_NOT_REPRODUCED`.
- Explicit delay/missing/duplicate/failed-transition assertion not reproduced: provider remains blocked. Status:
  `AI_SKIPPED_BY_EVIDENCE_GATE`.
- Provider-generated root-cause/fix fields are discarded in summary mode even if the provider returns them.
- A real invocation audit row is created only when the provider request occurs.

No database migration or environment-variable change is required for this evidence-gate fix. The audit migration
from the accompanying audit change remains `0009_llm_audit_outcomes.py`.
