# Investigation Accuracy and Evidence Validation Architecture Review

## Scope and correctness invariant

This review traces the production investigation path used by `/chat/ask`. It does not propose UI or product features. The governing invariant is:

> A final factual or causal statement may be stronger than an evidence gap only when the affected entity, relevant object, reported condition, and cited evidence have been deterministically verified; all collected evidence, including NULLs, zero-row results, failures, and contradictions, must remain available downstream.

## Lifecycle map

1. The chat route validates tenant/workspace access and classifies the request.
2. `detect_intent` and `extract_entities` produce deterministic intent and entity candidates.
3. Context discovery loads active-schema metadata and approved documents.
4. `resolve_entities` executes bounded lookups and either resolves, reports ambiguity, or blocks continuation.
5. Object ranking and procedure-definition matching select tables, views, diagnostics, and procedures.
6. The safe planner produces dialect-aware read-only SQL; the production safety validator applies policy and limits.
7. Evidence execution records rows, zero-row semantics, NULL semantics, execution failures, and policy decisions.
8. Related-ID expansion, procedure analysis, document retrieval, and correlation enrich the evidence package.
9. The evidence gate tests entity presence, condition reproduction, affected rows, and relationships; gap analysis records missing sources.
10. Deterministic reasoning separates facts, inferences, and hypotheses. Optional LLM reasoning receives an evidence registry and its claims pass claim verification.
11. Confidence scoring and report composition consume the same bundle; persisted investigation metadata and generated reports are downstream evaluation inputs.

## Detailed failure review

| Stage | Current behavior | Failure scenario | Root cause | Risk | Recommended fix | Expected accuracy improvement |
|---|---|---|---|---|---|---|
| User request / mode | Safety checks and deterministic mode classification route metadata, knowledge, business-rule, or live investigation paths. | Ambiguous wording selects a non-live mode and never tests the reported condition. | A single classification is treated as final; there is no downstream consistency check against extracted identifiers and requested factual verbs. | High: correct database evidence is never collected. | Add a deterministic mode-consistency assertion: exact business identifiers plus “why/failed/missing/duplicate” must enter a live evidence path unless the user explicitly requests documentation only. Persist the classification rationale. | Prevents complete false-negative investigations caused by early routing mistakes. |
| Intent detection | Rule-based intent returns one intent with confidence/rationale. | A process-flow missing-child case is classified only as generic production investigation, so specialized relationship queries are omitted. | Single-label intent collapses overlapping diagnostic needs. | High: wrong SQL plan and premature stopping. | Preserve secondary evidence requirements (missing relationship, duplicate, performance, job history) independently of the display intent and require planner coverage for each. | Improves query coverage without exposing a new user feature. |
| Entity extraction | Identifiers, codes, statuses, dates, and object names are extracted before metadata search. | A status/code is treated as the business key, or formatting differences prevent a match. | Entity types are lexical and lack schema/value provenance until resolution. | Critical: every later query can target the wrong record. | Keep the original and normalized entity, resolve candidate values only against active-schema columns, reject ambiguity, and persist table/column/evidence provenance. Existing resolution blocking should remain fail-closed. | Eliminates silent entity substitution and makes wrong resolution auditable. |
| Entity resolution | Bounded exact/safe-partial lookups return resolved, ambiguous, not-found, or blocked. | One resolved identifier overwrites every same-text extracted entity even when roles differ. | `_apply_entity_resolutions` keys replacements only by case-folded value, not entity role or resolution target. | Medium/high in multi-entity questions. | Key replacements by extraction occurrence/type and resolution trace; never globally replace equal text with different semantic roles. Add multi-entity regression cases. | Reduces cross-entity contamination in joins and filters. |
| Active schema / object discovery | Context discovery, scoring, exact-object traces, active diagnostics, and procedure definition matching build ranked metadata. | Relevant tables beyond ranking caps are not planned; a procedure is selected because generic tokens occur in its definition; FK paths spanning unranked bridge tables are missed. | Candidate narrowing occurs before complete relationship closure; token overlap is weaker than read/write and entity-column evidence. | Critical: wrong table/procedure and incomplete multi-object investigation. | Build a bounded relationship closure from the resolved entity table before ranking truncation. Rank procedures primarily by confirmed reads/writes of affected/relationship objects, with lexical match as a secondary signal. Persist rejected candidates and reasons. | Directly improves table/procedure precision and multi-object recall. |
| SQL planning | Intent-specific, dialect-aware read-only queries are deduplicated and capped. | The cap drops a distinct relationship or contradiction query after several redundant queries for the primary table. | Query limits are applied to a flat ranked list, not evidence obligations. | High: investigations stop with untested branches. | Allocate the query budget by coverage obligation (entity, reported condition, parent/child, writer, diagnostic source, contradiction check), then rank within each obligation. A terminal result must identify every uncovered obligation. | Increases deterministic coverage and reduces early false conclusions. |
| SQL validation / execution | SQL is dialect-checked, read-only validated, production-limited, executed, and assigned explicit status/semantics. | A failed/blocked query is treated as an empty successful query, or a changed safety query is cited as though the original ran. | Downstream code historically inferred state from `rows`/`error` instead of explicit execution fields. | Critical: absence claims and unsupported conclusions. | Require `execution_status == succeeded`; preserve original/executed SQL and policy decision; never derive absence from empty rows alone. These fields now persist with the evidence. | Removes false negatives from execution failures and makes the exact executed test reproducible. |
| Zero rows and NULL | Execution classifies verified absence and NULL-bearing rows; deterministic reasoning identifies verified NULL columns. | Any empty result is described as ruling out an alternative; NULL is formatted as an ordinary missing string or used as proof of a procedure defect. | Empty and NULL observations were sometimes summarized without semantic/relevance checks. | Critical: incorrect causal reasoning. | Count zero rows only when the query purpose/scope declares `verified_absence`; treat NULL as a positive observed value with column/evidence IDs, while keeping cause inconclusive unless procedure behavior is independently verified. Correlation and confidence now enforce these distinctions. | Eliminates a major class of false absence and NULL-causality claims. |
| Evidence collection / preservation | Evidence objects carry IDs, rows, semantics, relevance, support text, errors, and safety decisions. | Rows after the first ten disappear from persisted evidence; later evidence items disappear from text summaries. | Persistence stored samples as if canonical, and presentation used fixed slices. | Critical for benchmarks, audits, conflicts, and final reports. | Persist all rows already bounded by execution policy, retain `sample_rows` only as a compatibility view, mark truncation explicitly, and iterate over the full evidence list in evidence summaries. Implemented. | Ensures every collected fact remains available for validation and reporting. |
| Evidence correlation | SQL, procedure, and document evidence is normalized into correlated observations. | A zero-row query with unknown semantics receives medium confidence and reads like absence evidence. | Correlation used row count rather than verified evidence semantics. | High: weak observations become facts in reasoning. | Label only relevant `verified_absence` as high-confidence absence; mark other zero-row results low-confidence/unverified. Implemented. | Prevents unsupported negative evidence entering reasoning prompts/reports. |
| Conflicting evidence | Claim verification checks citation existence, prompt inclusion, zero-row validity, content support, and contradictions. | A claim cites a supporting row while omitting a conflicting collected row. | Contradiction checks were limited to claimant-selected citations. | Critical: citation cherry-picking yields a “verified” false claim. | Check each factual claim against the complete non-truncated evidence registry and return contradictory evidence IDs. Implemented. | Blocks internally inconsistent root-cause claims and preserves conflicts for review. |
| Evidence gate | Required intents verify business key, affected rows, reported condition, relationships, and normalized evidence categories before root-cause mode. | Procedure definitions or unrelated successful rows increase evidence availability even though they do not test the affected entity. | Legacy `not_applicable` row evidence has no semantic annotation. | High if availability is confused with causal support. | Keep legacy successful rows eligible only for constrained evidence summaries; explicit `irrelevant` evidence remains excluded, while confidence and claim verification require relevance and support. Keep primary-entity and relationship checks separate from evidence volume. Implemented. | Preserves factual backward compatibility without allowing unannotated rows to verify a root cause. |
| Multi-object continuation | Related IDs are expanded into additional active-schema tables; hypothesis/gap services can request more evidence in agentic flow. | The production synchronous path collects one initial plan plus bounded related IDs and may stop despite uncovered evidence obligations. | The agentic loop and production chat path are separate architectures; the main route does not always iterate on gaps. | High for workflows spanning tables/jobs/logs. | Converge both paths on one evidence-obligation loop. Continue until each required obligation is verified, explicitly unavailable/blocked, or budget-exhausted; terminal output must distinguish these states. | Largest expected recall improvement for multi-object root causes. |
| Deterministic root cause | Root-cause claims carry evidence refs and support status; summary-only modes suppress root cause and corrective action. | Generic “may be” causal templates are presented beside verified facts and can be mistaken for findings. | Hypothesis generation and final causal claims share similar prose. | High trust risk. | Permit only `VERIFIED` claims in Root Cause and Why It Happened. Put partial/unsupported items exclusively in Hypotheses with required missing evidence. Avoid causal recommendations when no verified claim exists. | Removes unsupported causal language from executive output. |
| Optional LLM reasoning | The model receives structured evidence and returned claims are parsed and verified. | Prompt size truncates rows but registry metadata still marks evidence as included; a claim depends on omitted values. | Inclusion/truncation must reflect the actual serialized prompt, not the pre-budget registry. | High under large investigations. | Construct the canonical registry after prompt-budget selection; mark every omitted/row-truncated reference and prohibit it from verifying a value claim. Preserve omitted evidence for deterministic conflict checks. | Prevents claims based on evidence the model never received. |
| Confidence | Confidence previously added points for any non-empty or empty result and object/procedure/doc presence. | Many irrelevant rows or unverified empty queries produce a high score despite unsupported root cause. | Confidence measured evidence volume/context availability, not verified claim coverage and contradictions. | Critical: overstates trustworthiness. | Score only relevant evidence with valid semantics/support, only count verified absence, penalize failed/gap/unsupported claims, and cap unreproduced required investigations. Implemented. | Aligns confidence with conclusion support; lowers false high-confidence reports. |
| Final report | The report bundle contains evidence, gate, reasoning, verification, gaps, procedure analysis, and traces; structured report evidence tables include all evidence. | Narrative answer/report summary omits later evidence or displays unverified root-cause text as executive cause. | Fixed presentation slices and mixed claim statuses. | Critical: collected facts disappear at the trust boundary. | Remove evidence-item slices, make the persisted complete evidence package canonical, derive executive root cause only from verified claims, and expose gaps/conflicts in the same report snapshot. Evidence slicing fixes are implemented; verified-claim isolation already exists in the report composer and should remain a release invariant. | Improves report completeness and prevents evidence/report divergence. |
| Persistence / evaluation | Investigation JSON stores evidence, structured result, gate trace, SQL, report snapshot, and entity provenance. | Evaluators see only samples, so a correct later row or contradiction is invisible and scores are unstable. | Persisted sample was the only row payload. | High: benchmark results do not reflect the actual investigation. | Persist complete bounded rows plus explicit sample/truncation metadata and teach readers to prefer `rows` with fallback to `sample_rows`. Implemented producer-side; consumers remain backward compatible. | Makes deterministic evaluation faithful and reproducible. |

## Implemented correctness changes

- Complete bounded result rows now persist under `rows`; the legacy ten-row `sample_rows` remains and is explicitly marked non-truncated.
- Evidence relevance, original SQL, executed SQL safety notes, and scan decisions remain attached to persisted evidence.
- Text evidence summaries and recommended investigation SQL no longer silently discard later evidence items.
- Unverified zero-row results are explicitly low-confidence observations, not absence evidence.
- Legacy successful `not_applicable` rows may unlock only a constrained evidence summary; explicit irrelevant rows are excluded, and they do not earn confidence or verify claims without relevance/support.
- Claim verification scans the complete included evidence registry for contradictions and returns the conflicting evidence IDs.
- Confidence uses verified relevant rows/absence, penalizes failures, evidence gaps, and unsupported claims, and caps required-but-unreproduced investigations.

## Release gates

Before merge, run the protected 25-scenario benchmark from a clean, correctly configured evaluation environment. A release should require:

- at least 95% deterministic accuracy;
- zero unsupported factual or causal claims;
- zero wrong-connection or wrong-entity investigations;
- every reported root cause backed by existing evidence IDs;
- every contradiction retained and reflected as rejection, ambiguity, or reduced confidence;
- exact NULL and zero-row semantics in persisted evidence and reports;
- no required evidence obligation silently omitted because of query/object/report caps.

Benchmark execution is an environment-level validation, not a substitute for the architectural and unit-level gates above.
